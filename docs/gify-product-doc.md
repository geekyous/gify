# Gify 开发文档

| 项 | 内容 |
|---|---|
| 版本 | v1.12（2026-10） |
| 形态 | 内网部署的轻量 AI Agent 平台 |
| 开发 | 单人开发 |
| 用户 | 20–50 人团队，内网环境 |

## 1. 概述

Gify 是部署在内网的轻量 AI Agent 平台：管理员注册模型服务，Agent 负责人配置 Agent（系统提示词、模型、工具、知识库），普通用户通过网页与 Agent 对话，管理员查看用量与成本。

基本使用流程：

1. 管理员部署平台、创建账号、接入模型供应商；
2. Agent 负责人配置并发布 Agent；
3. 普通用户在平台内或通过分享页使用 Agent；
4. 管理员与 Agent 负责人查看对话日志和用量统计。

## 2. 里程碑与功能清单

功能编号 FR-01 ~ FR-12 即全局开发顺序，按里程碑 M1（系统框架）→ M2（业务基础）→ M3（业务核心）推进。

### 2.1 M1 系统框架（开发阶段 ①）

 平台基础功能，不涉及 AI 业务。交付标准：可部署、可登录、可审计。

| 编号 | 功能 | 优先级 | 内容 | 依赖 |
|---|---|---|---|---|
| FR-01 | 用户与权限 | P0 | 三角色开号制，密码登录，权限隔离 | — |
| FR-02 | 部署与升级 | P0 | Compose 部署，数据迁移升级；初装随工程脚手架完成，升级验收在本里程碑末尾 | — |
| FR-03 | 操作审计 | P1 | 变更操作统一写入审计日志，管理端可筛选 | FR-01 |

### 2.2 M2 业务基础（开发阶段 ②③④）

可复用的 AI 引擎层：模型接入、对话引擎、知识库检索、工具调用。交付形态为内测版（极简调试界面），界面产品化在 M3 完成。技术难点共 4 个，其中 3 个（FR-05/06/07）在本里程碑。

| 编号 | 功能 | 优先级 | 内容 | 依赖 |
|---|---|---|---|---|
| FR-04 | 模型供应商管理 | P0 | Provider 与 Model 注册、连接测试、平台默认模型 | FR-01 |
| FR-05 | 对话引擎 | P0 | 流式输出、多轮上下文、会话持久化 | FR-04 |
| FR-06 | 知识库 + RAG | P0 | 固定摄取管道，检索测试页 | FR-04 |
| FR-07 | MCP 工具接入 | P0 | 工具调用循环 + MCP 客户端，附内置工具服务器 | FR-05 |

### 2.3 M3 业务核心（开发阶段 ⑤⑥⑦）

## 3. 功能规格

### FR-01 用户与权限（M1 / P0）

**需求说明**

为平台提供账号体系与权限控制。平台仅面向内部团队，不提供自助注册和邮箱验证，账号由管理员统一创建与维护，对应内部场景：入职开号，离职禁用。

设三种角色：管理员（admin）、Agent 负责人（builder）、普通用户（user）。界面与本文档使用中文名，系统内角色标识使用英文，各角色能力见下方矩阵。

**角色权限矩阵**

| 能力 | 管理员 | Agent 负责人 | 普通用户 |
|---|:---:|:---:|:---:|
| 系统设置（模型供应商、MCP Server） | ✓ | — | — |
| 用户管理 | ✓ | — | — |
| 操作审计查看 | ✓ | — | — |
| 创建 / 配置 Agent | ✓ | ✓ | — |
| 知识库管理 | ✓ | ✓ | — |
| 对话日志 / 统计 | 全量 | 本人 Agent 范围 | — |
| 平台内使用 Agent | ✓ | ✓ | ✓ |

**功能要求**

1. 密码登录，口令以 bcrypt 或 argon2 哈希存储。
2. 会话管理使用 JWT 或服务端 session。
3. 初始管理员账号由部署脚本生成，首次登录强制修改密码。
4. 用户被禁用后，其存量登录会话立即失效。
5. 用户管理操作：创建用户、编辑角色、重置密码、禁用。

**验收标准**

1. 管理员可创建、禁用用户并分配角色；禁用后该用户在线会话即时失效。
2. Agent 负责人访问系统设置返回 403；普通用户仅能看到 Agent 使用入口。
3. 未登录访问任何页面跳转登录页。

**依赖**：无

### FR-02 部署与升级（M1 / P0）

**需求说明**

定义平台的交付形态与升级方式。目标环境为内网单机部署、单人运维，升级路径的优先级高于初装体验。范围仅覆盖初装、升级与日志查看，不包含监控、告警等运维能力。

**功能要求**

1. `docker-compose.yml` 包含四个容器：app（API）、nginx（前端静态托管，与 API 跨域）、PostgreSQL（含 pgvector 扩展）、Redis。
2. `.env` 配置端口、密钥、初始管理员账号、CORS 白名单与前端注入的 API 地址（`VITE_API_BASE_URL`）。
3. 升级流程：拉取新镜像 + 执行 `migrate` 脚本（数据迁移）；升级前提示备份（`pg_dump` + volumes）。
4. 系统日志结构化输出到 stdout，通过 `docker compose logs` 查看，不做日志检索界面。

**验收标准**

1. 全新机器执行 `docker compose up` 后 5 分钟内可登录。
2. 执行一次升级，对话、知识库、配置、审计数据无丢失。

**依赖**：无

### FR-03 操作审计（M1 / P1）

**需求说明**

记录平台内的配置变更历史，回答谁在何时修改了什么，用于追溯与排障。定位为操作历史级审计，不做合规级存证（不可篡改、签名导出等）。

**功能要求**

1. 审计记录包含：操作人、动作（创建 / 更新 / 删除）、对象类型与标识、变更摘要或前后对比、时间。
2. 所有变更类操作（Agent、知识库、Provider、MCP Server、用户、分享）经统一变更入口自动写入审计日志，业务代码不感知；审计记录只追加，不提供修改与删除接口。
3. 管理端提供按操作人、对象类型、时间筛选的审计列表。
4. Agent 配置页头部显示最近修改人与修改时间，数据取自审计记录。

**验收标准**

1. 修改提示词、更换默认模型、新增用户、开启分享均产生审计记录。
2. 审计记录不可通过界面修改或删除。
3. Agent 配置页可见最近修改人与时间。

**依赖**：FR-01

### FR-04 模型供应商管理（M2 / P0）

**需求说明**

平台唯一的模型接入入口：部署完成后，管理员需先注册模型供应商，平台才能提供对话与嵌入能力。仅支持 OpenAI 兼容协议，以一条代码路径覆盖 vLLM、Ollama、DeepSeek、Qwen 及各类中转网关，不接入其他协议的模型服务。

**功能要求**

1. 接入流程：新建 Provider → 测试连接（调用 `/v1/models` 验证）→ 自动导入模型列表 → 勾选启用、补全元数据 → 设置平台默认模型（默认 chat 模型与默认 embedding 模型）。
2. 模型元数据：类型（chat / embedding）、能力标记（tool_call、vision、上下文长度）、单价（每 1M token，选填，区分输入 / 输出）。
3. 能力过滤：配置了工具的 Agent，其模型下拉列表只显示具备 tool_call 能力的模型。
3. 计价降级：未配置单价的模型，统计中降级显示 token 数。
4. 禁用语义：Provider 禁用后，其模型从新配置的可选列表中消失；已配置 Agent 的历史记录不受影响。
5. api_key 加密落库，任何日志不得记录明文。

**验收标准**

1. 接入 vLLM 或外部 API 后"测试连接"一次通过。
2. 从 `/v1/models` 拉取的模型列表可勾选启用并编辑元数据。
3. tool_call 过滤、单价降级、禁用语义按上述规则生效。

**依赖**：FR-01

### FR-05 对话引擎（M2 / P0 / 技术难点）

**需求说明**

平台所有对话能力的执行核心，对上提供统一的对话执行接口。引擎先于界面交付：以 API 形式实现并可直接被脚本调用，界面只是其消费者之一。

**功能要求**

1. 统一执行签名：所有执行单元实现 `run(context) → result`；context 包含消息历史、变量、Agent 配置引用。该签名供分流与 v2 串行链复用同一内核。
2. 流式输出：SSE 逐 token 推送；每轮消息服务端先落库，断线刷新后不丢历史。
3. 会话持久化：会话归属 Agent 与用户，记录来源（平台 / 分享页）并自动生成标题；消息记录角色、内容、token 用量。
4. 用量记录：优先使用 API 返回的 usage；缺失时按 tokenizer 估算（部分本地推理服务不返回 usage）。
5. 记忆：携带最近 N 轮上下文（N 为 Agent 配置项），超出截断。

**验收标准**

1. 回答逐字流式呈现，刷新后会话历史完整。
2. 每轮 token 用量入库（含估算降级路径）。
3. 引擎可通过同一 API 被脚本调用，不依赖界面。

**依赖**：FR-04

### FR-06 知识库 + RAG（M2 / P0 / 技术难点）

**需求说明**

为 Agent 提供基于内部文档的检索问答能力（RAG）。采用固定摄取管道，不做可配置管道。

**功能要求**

1. 摄取管道：上传（txt / md / pdf / docx）→ 文本抽取 → 分块（固定大小 + 内置重叠）→ 嵌入 → 向量入库。
2. 可调参数两个：chunk size、top-k。
3. 嵌入模型在创建知识库时选定并锁定在 KB 记录上；修改平台默认嵌入模型不影响已有库；更换嵌入模型等于全量重建索引，UI 需显式警告。
4. 检索测试页：输入 query，展示 top-k 分块、命中分数、所属文档。
5. 删除文档时同步删除其全部分块与向量。
6. 知识库列表显示：容量、文档数、分块数、嵌入模型。

**验收标准**

1. 上传四种格式文件后检索可命中。
2. 检索测试页显示 top-k 结果与命中分数。
3. 更换平台默认嵌入模型后，旧库行为不变，且建库页有相应警告。

**依赖**：FR-04

### FR-07 MCP 工具接入（M2 / P0 / 技术难点）

**需求说明**

为 Agent 提供调用外部工具的能力。工具统一通过 MCP（Model Context Protocol）接入：平台作为 MCP 客户端，内置工具与后续自研工具均以 MCP Server 形式注册，新增工具不需要修改平台代码。

**功能要求**

1. 调用循环：模型返回 tool_call → 执行 → 结果作为 observation 回填 → 继续循环，上限 N 轮（默认 5）→ 产出最终回答。
2. MCP Server 管理：管理员在系统设置中注册 MCP Server，内容包括名称、传输方式（stdio 启动命令或 HTTP URL）、环境变量与鉴权信息（选填，鉴权信息加密存储）；支持测试连接、启用 / 禁用。
3. 工具发现：从已启用的 MCP Server 拉取工具列表，转换为模型可用的 function 定义；Agent 配置中以 `server:tool` 格式勾选可用工具。
4. 内置工具服务器：随平台附带一个内置 MCP Server（名称 `builtin`），提供三个工具：
   - `builtin:web_search(query)`：网页搜索；
   - `builtin:fetch_url(url)`：抓取网页正文；
   - `builtin:http_request(method, url, headers, body)`：通用 HTTP 请求，可访问内网。标记为高风险工具，分享页上的 Agent 默认不开放。
5. 失败处理：工具报错或超时（默认 10 秒）不向用户抛出异常，作为 observation 交给模型解释或改换路径。
6. 每次调用写入步骤日志：工具名（`server:tool`）、入参、返回摘要、耗时、状态。

**验收标准**

1. 通过内置工具服务器挂载搜索工具的 Agent 能查询实时信息并说明来源。
2. 注册一个自编写的 MCP Server 后，其工具无需修改平台代码即可被 Agent 挂载使用。
3. 工具失败时 Agent 向用户解释原因，不崩溃、不输出编造内容。
4. 每次工具调用在日志中完整可见。

**依赖**：FR-05

### FR-08 Agent 创建与配置（M3 / P0）

**需求说明**

Agent 负责人的主要工作界面，完成 Agent 从创建到发布生效的全过程配置。保存即生效，v1 不提供草稿与版本机制。

**功能要求**

1. 配置分区：基本信息（名称、描述、图标）、提示词、模型（按能力过滤）、工具勾选（从已启用的 MCP 工具中选择）、知识库挂载、记忆（开关与上下文轮数）。
2. 每次配置变更写审计并显示最近修改人。
3. 配置页右侧常驻调试对话面板（延续 M2 内测形态），修改后可立即验证。
4. 单工作区：Agent 负责人之间互相可见 Agent。
5. 平台内普通用户可见全部启用中的 Agent。

**验收标准**

1. 无代码完成"提示词 + 知识库 + 工具"的 Agent 配置并立即试用。
2. 配置变更即时生效并产生审计记录。
3. 模型下拉按 tool_call 能力过滤。

**依赖**：FR-04 / FR-05 / FR-06 / FR-07

### FR-09 与 Agent 对话（M3 / P0 / 技术难点）

**需求说明**

普通用户使用平台的主要入口，提供会话管理与对话的全部使用侧功能，不含任何配置能力。

**功能要求**

1. 会话列表按 Agent 分组、按时间排序；支持新建、删除会话，历史回看。
2. 流式渲染，支持 Markdown、代码块、复制。
3. 专家标签：分流场景下，每条回复标注本轮命中的专家 Agent（如"技术支持"）。
4. 会话按用户隔离；用户删除会话不影响管理端日志。
5. 首次进入引导：无可用 Agent 时提示联系 Agent 负责人。

**验收标准**

1. 登录后可见可用 Agent，会话按用户隔离。
2. 历史会话可回看完整上下文。
3. 分流场景的回复带专家标签。

**依赖**：FR-05 / FR-08

### FR-10 智能分流（M3 / P1）

**需求说明**

提供一个对话入口接入多个专家 Agent 的能力：系统按每轮用户输入判断由哪个 Agent 应答，用户无需选择。采用两级分类的固定方案，全部通过配置完成，不提供画布式编排。

**功能要求**

1. 两级分类：规则（正则，按序匹配，先命中先用）→ LLM 兜底（结构化输出，temperature=0，携带最近几轮上下文）→ 默认路由。
2. 配置构成：分类规则（正则与目标类别）、LLM 分类设置（分类模型可单独指定；类别列表，每个类别含标识与描述）、路由表（类别到 Agent 的映射，含默认路由）。
3. 每轮分类：同一会话内切换话题时自动切换目标 Agent。
4. 共享上下文：同一份对话记录，按轮切换目标 Agent 的提示词、工具、知识库。
5. 异常兜底：LLM 分类失败、规则未命中时，一律路由到默认路由，不向用户报错。
6. 分流测试页：输入示例问句，显示命中路径与原因（规则 / LLM）。
7. 类别描述是影响分类准确率的主要配置项，配置页对此重点引导。
8. 边界：单层路由不嵌套；不做置信度阈值；混合意图取主要意图。

**验收标准**

1. 三类示例问句各自命中正确 Agent。
2. 规则未命中的模糊表达由 LLM 正确分类。
3. LLM 失败时落入默认路由，用户无感知。
4. 分流测试页显示命中原因。

**依赖**：FR-05 / FR-08

### FR-11 对话日志与用量成本（M3 / P1）

**需求说明**

为管理员与 Agent 负责人提供对话日志查询和用量成本统计，用于排障、调优与成本核算。

**功能要求**

1. 日志结构：`run_id → step_id → 输入 / 输出 / 耗时 / token`；每个 run 记录来源（平台 / 分享页）与路由结果。
2. 日志页：按 Agent、用户、时间筛选；展开任意一轮可见完整消息、路由结果、工具调用链、token 与耗时。
3. 统计页：维度为 Agent × 用户 × 时间；指标为调用次数、token、成本（Σ token × 模型单价）；模型未配置单价时降级显示 token。
4. 预设视图：本月各 Agent 成本排行、活跃用户排行。
5. 权限：Agent 负责人可见本人 Agent 范围内的日志，管理员可见全量。

**验收标准**

1. 任意一轮问答可展开完整轨迹。
2. 可直接回答"本月哪个 Agent 消耗多少成本"。
3. 分享页来源的对话可与平台内对话区分。

**依赖**：FR-04 / FR-05

### FR-12 分享页使用（M3 / P1）

**需求说明**

为 Agent 提供免登录的内网使用入口，面向不使用平台账号的同事。

**功能要求**

1. 生命周期：开启分享 → 生成 token 化链接 → 关闭后立即失效；链接绑定 Agent。
2. 免登录：内网可达即可使用；匿名会话独立存储，来源标记为分享页，用量归入该 Agent 的日志与统计。
3. 界面：极简聊天页（Agent 名称、对话框、免责提示），不含任何管理功能。
4. 安全约束：分享页 Agent 默认不开放高风险工具（如 `builtin:http_request`）；不暴露系统提示词与内部配置。

**验收标准**

1. 内网打开分享链接即可对话，无需登录。
2. 关闭分享后链接立即失效。
3. 分享页对话在日志中可按来源区分。

**依赖**：FR-08 / FR-09

## 4. 范围边界

若业务发展到需要画布编排，应改用 Dify 等平台，不在本平台内扩展。

## 5. 技术规范

### 5.1 接口与协议

1. REST API：每个 Agent 一个对话端点（SSE 流式）；产品前端与内部系统集成共用同一套 API，前端是 API 的第一个消费者。
2. 模型协议：仅 OpenAI 兼容（base_url + key + 模型列表）。
3. 嵌入一致性：知识库创建时锁定嵌入模型；更换模型需重建索引，UI 显式警告。
4. 工具协议：MCP（Model Context Protocol），平台作为 MCP 客户端接入工具服务器，内置与自研工具均以 MCP Server 形式注册。

### 5.2 架构约定

1. 统一签名 `run(context) → result`：Agent、分流器、未来节点使用同一接口。
2. context 与逻辑分离：显式对象贯穿传递；串行执行的实质是同一 context 依次流过 N 个节点。
3. 配置存 JSONB：不建固定列；v2 的 chain steps 是同表的另一种 config。
4. 日志按步骤结构化：`run_id → step_id → 输入 / 输出 / 耗时 / token`。
5. 后端为领域模块化单体：identity、providers、engine、kb、tools、agents、chat、usage 八个模块，模块间只经对方 service 公开函数交互；对话引擎不依赖 Web 请求上下文，可被 API、后台任务、脚本以同一入口调用。
6. 外部系统调用（模型服务、MCP Server）在所属模块的 client 层收口，超时重试与密钥处理不散落在业务代码。

### 5.3 日志与审计

1. 审计：变更经统一入口写 `audit_log` 追加表。
2. 系统日志：结构化输出 stdout，通过 `docker compose logs` 查看，不做检索界面。

### 5.4 技术栈与部署

技术选型（2026-10 确认）：

| 层 | 选型 | 说明 |
|---|---|---|
| 后端 | Python 3.12+ / FastAPI | ORM：SQLAlchemy 2.0；迁移：Alembic；依赖管理：uv |
| 前端 | Vue 3 + TypeScript + Vite + Element Plus | 状态：Pinia；Markdown 渲染：markdown-it |
| 数据库 | PostgreSQL 16 + pgvector | 业务数据与向量同库，一套备份 |
| 缓存 / 队列 | Redis 7 | session 存储、RAG 摄取队列 |
| 模型接入 | openai SDK | 仅 OpenAI 兼容协议，base_url 可指向任意兼容服务 |
| 工具接入 | MCP 官方 Python SDK | 平台作为 MCP 客户端 |
| 认证 | 服务端 session（cookie） | session 存 Redis，用户禁用后即时失效 |
| 文档解析 | pypdf、python-docx | txt / md 原生处理 |
| token 估算 | tiktoken | API 未返回 usage 时降级估算 |
| 后台任务 | arq | RAG 摄取管道：解析 → 分块 → 嵌入 → 入库 |

部署：Docker Compose 四容器（app、nginx、PostgreSQL、Redis）；前端由独立 nginx 容器托管，与 API 跨域，构建时注入 `VITE_API_BASE_URL`，后端经 CORS 白名单（`CORS_ORIGINS`）放行，会话凭证随跨域请求携带；升级流程含数据迁移（Alembic）。

### 5.5 开发节奏约束

1. 技术难点共 4 个：FR-05（对话引擎）、FR-06（RAG）、FR-07（工具循环 + MCP 客户端）、FR-09（对话界面），其余为常规 CRUD。
2. 任何模块的计划外投入超过计划时间的 10% 时，重新评估该模块的范围，防止偏离 MVP。
